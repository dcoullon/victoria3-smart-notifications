# Phase 4 -- Relational Notification Engine (see TODO.md). The actual
# payoff of the Watchlist feature: elevate a diplomatic play's
# notification when a watched country (or the player) is involved,
# demote it to the ambient feed otherwise.
#
# Scope for this first pass (confirmed with the user 2026-09-07): the
# three Diplomatic-Play-rooted events with a clean, confirmed hook --
# play started, someone joined a side, and the play became a war. War
# end/peace already gets popup+treaty-terms coverage from Phase 2's
# existing (unconditional) peace/capitulation notifications, and
# invasions have no moddable hook for 3 of their 4 keys (see the Dev
# Tooling section of TODO.md) -- both deferred rather than bolted on
# incompletely.
#
# Extended 2026-09-07 with the 3 genuinely third-party keys identified in
# TODO.md's "Third-party notification filtering" inventory that also root
# on Diplomatic Play: diplo_play_start_third_party_notification,
# diplo_play_subject_released_notification, and
# diplo_play_war_start_third_party_notification. The remaining ~15
# third-party keys stay blocked/unbuilt per that inventory -- Country-rooted
# ones need the other side of the relationship, Diplomatic-Action/Pact-rooted
# ones have no documented scope link out at all.
#
# CORRECTED 2026-09-07, same day, after the user's first real playtest
# turned up two real bugs in the initial third-party wiring:
# 1. **Duplicate notifications.** on_diplo_play_start/on_diplo_play_start_third_party
#    (and, inline, the two war_start keys) turned out NOT to be two
#    different channels reaching two different audiences as assumed --
#    confirmed via matching timestamps/actor/target in a real SNW_FILTER
#    log: both fired for the exact same play, to the same (single-player)
#    viewer, producing two near-identical entries for one event. Since
#    `smart_notifications_is_watched` already ORs in `is_player = yes`
#    (00_smart_notifications_triggers.txt), the third-party channel alone
#    already captures "the player is involved" -- nothing is lost by
#    posting from only one of the two on_actions per event.
# 2. **Blank target text on `on_diplo_play_start` specifically.** The same
#    log showed `target=` resolving empty ONLY for this one on_action --
#    every other diplo-play on_action (war_start, join_side,
#    start_third_party, subject_released) resolved it fine. This lines up
#    with vanilla's OWN loc for `diplo_play_start_notification` (the
#    primary, non-third-party key) never referencing scope:target at all
#    ("...against us", no named target) -- strong evidence scope:target
#    genuinely isn't bound yet at the exact moment a play starts (its
#    target may not be settled until slightly later), while it reliably is
#    by the time on_diplo_play_start_third_party/on_diplo_play_war_start
#    fire.
# Fix: consolidated to ONE notification per event, always posted from
# whichever on_action's scopes are confirmed reliable. `on_diplo_play_start`
# is no longer hooked at all -- the "did a play start" notification now
# posts from on_diplo_play_start_third_party instead (reusing the
# ORIGINAL smart_notifications_diplo_play_start_watched/_quiet keys and
# their toast/feed tiers, not the separate third-party-flavored keys,
# which are deleted as redundant). `on_diplo_play_war_start` keeps its own
# hook (its scope:target already resolved correctly) but no longer also
# posts the separate third-party pair. diplo_play_start_third_party_notification
# and diplo_play_war_start_third_party_notification (the vanilla keys)
# stay muted (`none`, 00_messages.txt) with no mod replacement of their
# own -- their event is now fully covered by the consolidated channel
# above.
#
# Per the modding rules in the game's own common/on_actions/_on_actions.md
# (and CLAUDE.md): never redefine a vanilla on_action's effect directly,
# append our own on_action name to its `on_actions = {}` list instead.
# Root = Diplomatic Play for all of these (confirmed via vanilla's own
# comments in common/on_actions/00_code_on_actions.txt).
#
# Per CLAUDE.md's override-hierarchy note: post_notification can't switch
# notification_type per call, so "toast for watched, feed for everyone
# else" on what's conceptually one event needs two separate keys/groups,
# chosen here by script. Confirmed with the user (2026-09-07): this
# REPLACES the existing vanilla notification for these groups (muted to
# `none` in common/messages/00_messages.txt) rather than adding an extra
# alert alongside it, so a watched play produces exactly one notification,
# not two.

# ADDED 2026-09-09 -- the fix for a confirmed, serious gap: a diplomatic
# play declared ON THE PLAYER produced no notification at all.
#
# The 2026-09-07 note below concluded that on_diplo_play_start and
# on_diplo_play_start_third_party were two channels for the same event, and
# dropped the former on the strength of a log where both fired for one play.
# That generalised from a play the player was a BYSTANDER to. A live session
# 2026-09-09 shows the opposite for the case that matters: Great Britain
# opened a play against the player, `on_diplo_play_start` fired (twice in the
# session, per the frequency logger) and `on_diplo_play_start_third_party`
# fired **not once** -- the whole session logged zero `SNW_FILTER|start`
# decisions. Because vanilla's own `diplo_play_start_notification` (the
# "X started a play against us" key) is muted by this mod, the result was
# total silence for someone declaring a play on you. The single worst
# failure this mod can have, and it shipped.
#
# Both hooks now post, and the dedup guard already on the shared handler is
# what stops a play that somehow fires both from notifying twice: it is a
# flag on the diplomatic play itself (root), so it spans both on_actions
# rather than being per-hook.
on_diplo_play_start = {
	on_actions = {
		smart_notifications_diplo_play_start
	}
}

on_diplo_play_start_third_party = {
	on_actions = {
		smart_notifications_diplo_play_start
	}
}

on_diplo_play_join_side = {
	on_actions = {
		smart_notifications_diplo_play_join_side
	}
}

on_diplo_play_war_start = {
	on_actions = {
		smart_notifications_diplo_play_war_start
	}
}

on_diplo_play_subject_released = {
	on_actions = {
		smart_notifications_diplo_play_subject_released
	}
}

# Shared "is this diplomatic play worth a prominent notification" check,
# duplicated inline in each on_action below (scripted triggers can't be
# shared as a value the way effects can via a variable, and these need
# to run inside the SGUI/on_action's own `if` block) rather than
# factored into common/scripted_triggers/, since only these three
# on_actions use it -- revisit if a fourth caller shows up.
#
# CORRECTED 2026-09-08, real bug found via the user's second playtest:
# `any_scope_play_involved = { smart_notifications_is_watched = yes }`
# alone was WRONG -- confirmed via two real revolutions (Bali, Sulu) that
# showed Great Britain, United Netherlands, Portugal and Spain (this
# mod's whole watchlist) all counting as "involved" despite having zero
# connection to either country's internal politics, elevating both to a
# toast the user rightly called "super painful". `any_scope_play_involved`
# ("Iterate through all involved in a: diplomatic play", confirmed real
# via effects.log) evidently includes every eligible-but-uncommitted
# potential intervener, not just genuine committed sides -- essentially
# any Great Power, for any play, anywhere, since Great Powers are broadly
# eligible to intervene in nearly everything. Tried
# `is_diplomatic_play_committed_participant` as a narrower replacement
# first; ALSO wrong, confirmed the same way (Great Britain/Netherlands
# showed `committed=yes` for both unrelated revolutions) -- turned out to
# be a GLOBAL check ("is this country committed to ANY diplomatic play
# right now", per triggers.log), so a Great Power committed to some
# unrelated play elsewhere in the world still false-positives.
# `is_diplomatic_play_participant_with = scope:actor` (pairwise, "is this
# country a committed participant in the SAME diplomatic play as
# scope:actor") is the one that's actually correct: confirmed against
# both Bali and Sulu, only the real actor/target ever showed
# `participant_with_actor=yes`, every Great Power correctly showed `no`.
# ANDed with `smart_notifications_is_watched` below so only a WATCHED
# genuine participant elevates the play -- the Watchlist's 4 flags (plus
# `is_player = yes`, baked into smart_notifications_is_watched itself)
# are still the pre-computed answer to "do we care", just now gated on
# actually being in the play rather than merely eligible to join it.

# Root = Diplomatic Play. Hooked from on_diplo_play_start_third_party, NOT
# on_diplo_play_start -- see the header comment's "CORRECTED 2026-09-07"
# note: scope:target isn't reliably bound yet at the on_diplo_play_start
# moment (confirmed via a blank target= in a real playtest log), but is by
# the time this on_action fires. Posts the original watched/quiet keys
# (toast/feed), not third-party-flavored ones -- this is the sole
# notification for "a diplomatic play started" now, covering both what
# used to be two separate (and duplicating) channels.
smart_notifications_diplo_play_start = {
	effect = {
		# DEDUP GUARD (2026-09-08) -- a real session showed this exact
		# on_action firing 13 TIMES in the same second for one real
		# "Cambodia sides with Nepal"-shaped event (see join_side below,
		# same fix applied to all 4 events in this file since the on_action
		# invocation, not our own script, is what's repeating). Root
		# (the diplomatic play) persists across all those repeat calls, so
		# a short-lived flag on root -- confirmed-real vanilla pattern,
		# `set_variable = { name = X value = yes days = N }`, e.g.
		# ai_expedition_cooldown in common/decisions/*_expedition_decision.txt
		# -- collapses the burst into a single notification. Known
		# tradeoff, accepted: two genuinely different actors starting a
		# NEW play against the same target on the same day would also be
		# collapsed to one notification; far better than 13x spam.
		if = {
			limit = { NOT = { has_variable = smart_notifications_start_notified_recently } }
			set_variable = { name = smart_notifications_start_notified_recently value = yes days = 1 }
			# F2 player tier (docs/watchlist-spec.md), added 2026-09-09.
			# Checked BEFORE the watched branch because the player counts
			# as watched (00_smart_notifications_triggers.txt) and would
			# otherwise be swallowed by it -- which is exactly what used to
			# happen, conflating "someone brought a play to me" with "a
			# country I follow joined one somewhere".
			#
			# `scope:actor` excluded explicitly: spec invariant 5, a play
			# YOU started is never promoted. It still falls through to the
			# watched branch below, which is today's behaviour and what the
			# user asked to keep.
			# Nothing at all when the PLAYER opened this play, matching
			# vanilla. Confirmed by a control test on a mod-free game
			# 2026-09-10: vanilla's diplo_play_start_notification is worded
			# "X started a play against us" and fires only for the target, so
			# it never appears for a play you opened yourself. This mod mutes
			# that key and posts its own, and because the player counts as
			# watched, the play you just declared fell into the watched branch
			# and toasted back at you.
			#
			# Checked FIRST, before the player and watched branches, since
			# actor-is-player would otherwise be swallowed by either. Applied
			# to play start only -- join side is untested and vanilla's key
			# there is not worded "against us", so it probably does fire for
			# every join including your own.
			if = {
				limit = { scope:actor ?= { is_player = yes } }
				debug_log = "SNW_FILTER|start|posted_key=NONE_PLAYER_IS_ACTOR|actor=[SCOPE.sC('actor').GetNameNoFormatting]|SELF_INITIATED"
			}
			else_if = {
				# Two ways to be "the player is in this play", OR'd, because
				# neither alone is reliable on every hook in this file:
				#
				# - scope:target is the direct answer but is NOT dependably
				#   bound at on_diplo_play_start (see the 2026-09-07 note in
				#   the header -- target= logged empty there, and vanilla's
				#   own loc for that key never references it either). `?=`
				#   makes an unbound scope fail the branch instead of
				#   erroring.
				# - any_scope_play_involved + is_diplomatic_play_participant_with
				#   is the reliable one later on, but it asks about COMMITTED
				#   participants, and the target of a brand-new play may not
				#   be committed yet at the instant it opens.
				#
				# Either matching is enough. Getting this wrong in the safe
				# direction costs a toast instead of a popup; getting it wrong
				# the other way is the silence bug this file just had.
				limit = {
					scope:actor ?= { NOT = { is_player = yes } }
					OR = {
						scope:target ?= { is_player = yes }
						any_scope_play_involved = {
							is_diplomatic_play_participant_with = scope:actor
							is_player = yes
						}
					}
				}
				post_notification = smart_notifications_diplo_play_start_player
				debug_log = "SNW_FILTER|start|posted_key=smart_notifications_diplo_play_start_player|actor=[SCOPE.sC('actor').GetNameNoFormatting]|target=[SCOPE.sC('target').GetNameNoFormatting]|PLAYER_INVOLVED"
			}
			else_if = {
				limit = {
					any_scope_play_involved = {
						is_diplomatic_play_participant_with = scope:actor
						smart_notifications_is_watched = yes
					}
				}
				post_notification = smart_notifications_diplo_play_start_watched
				debug_log = "SNW_FILTER|start|posted_key=smart_notifications_diplo_play_start_watched|actor=[SCOPE.sC('actor').GetNameNoFormatting]|target=[SCOPE.sC('target').GetNameNoFormatting]|ELEVATED"
			}
			else = {
				post_notification = smart_notifications_diplo_play_start_quiet
				debug_log = "SNW_FILTER|start|posted_key=smart_notifications_diplo_play_start_quiet|actor=[SCOPE.sC('actor').GetNameNoFormatting]|target=[SCOPE.sC('target').GetNameNoFormatting]|QUIET"
			}
		}
		else = {
			debug_log = "SNW_FILTER|start|DUPLICATE_SUPPRESSED"
		}

	}
}

smart_notifications_diplo_play_war_start = {
	effect = {
		# DEDUP GUARD (2026-09-08) -- see smart_notifications_diplo_play_start's
		# copy of this guard above for the full writeup (confirmed 13x
		# repeat firing for one join_side event; applied defensively to
		# all 4 events in this file, not just the one directly observed).
		if = {
			limit = { NOT = { has_variable = smart_notifications_war_start_notified_recently } }
			set_variable = { name = smart_notifications_war_start_notified_recently value = yes days = 1 }
			# F2 player tier (docs/watchlist-spec.md), added 2026-09-09.
			# Checked BEFORE the watched branch because the player counts
			# as watched (00_smart_notifications_triggers.txt) and would
			# otherwise be swallowed by it -- which is exactly what used to
			# happen, conflating "someone brought a play to me" with "a
			# country I follow joined one somewhere".
			#
			# `scope:actor` excluded explicitly: spec invariant 5, a play
			# YOU started is never promoted. It still falls through to the
			# watched branch below, which is today's behaviour and what the
			# user asked to keep.
			if = {
				# Two ways to be "the player is in this play", OR'd, because
				# neither alone is reliable on every hook in this file:
				#
				# - scope:target is the direct answer but is NOT dependably
				#   bound at on_diplo_play_start (see the 2026-09-07 note in
				#   the header -- target= logged empty there, and vanilla's
				#   own loc for that key never references it either). `?=`
				#   makes an unbound scope fail the branch instead of
				#   erroring.
				# - any_scope_play_involved + is_diplomatic_play_participant_with
				#   is the reliable one later on, but it asks about COMMITTED
				#   participants, and the target of a brand-new play may not
				#   be committed yet at the instant it opens.
				#
				# Either matching is enough. Getting this wrong in the safe
				# direction costs a toast instead of a popup; getting it wrong
				# the other way is the silence bug this file just had.
				limit = {
					# NO actor exclusion here, unlike the start and join-side
					# families above. Invariant 5 says your own ACTIONS are
					# never news -- you clicked the button, you know. A war
					# actually breaking out is not that: it arrives later, as
					# a consequence, and vanilla pops it up regardless of who
					# started the play. Confirmed the hard way 2026-09-10 --
					# the user declared war on Russia and got a toast instead
					# of the popup, because this branch skipped them for being
					# the actor.
					OR = {
						# The player started it. Tested directly, because
						# is_diplomatic_play_participant_with = scope:actor
						# asks about participants WITH the actor and may well
						# not count the actor itself -- so removing the
						# exclusion above is not on its own enough to detect
						# a war the player declared.
						scope:actor ?= { is_player = yes }
						scope:target ?= { is_player = yes }
						any_scope_play_involved = {
							is_diplomatic_play_participant_with = scope:actor
							is_player = yes
						}
					}
				}
				# Deliberately posts NOTHING. Vanilla's own
				# diplo_play_war_start_notification is un-muted again and
				# handles every war involving the player -- its popup, its
				# sound, and crucially its default pause, which a key of ours
				# cannot have. Posting here as well is what produced the
				# double popup of 2026-09-08.
				debug_log = "SNW_FILTER|war_start|posted_key=NONE_VANILLA_HANDLES_IT|actor=[SCOPE.sC('actor').GetNameNoFormatting]|target=[SCOPE.sC('target').GetNameNoFormatting]|PLAYER_INVOLVED"
			}
			else_if = {
				limit = {
					any_scope_play_involved = {
						is_diplomatic_play_participant_with = scope:actor
						smart_notifications_is_watched = yes
					}
				}
				post_notification = smart_notifications_diplo_play_war_start_watched
				debug_log = "SNW_FILTER|war_start|posted_key=smart_notifications_diplo_play_war_start_watched|actor=[SCOPE.sC('actor').GetNameNoFormatting]|target=[SCOPE.sC('target').GetNameNoFormatting]|ELEVATED"
			}
			else = {
				post_notification = smart_notifications_diplo_play_war_start_quiet
				debug_log = "SNW_FILTER|war_start|posted_key=smart_notifications_diplo_play_war_start_quiet|actor=[SCOPE.sC('actor').GetNameNoFormatting]|target=[SCOPE.sC('target').GetNameNoFormatting]|QUIET"
			}
		}
		else = {
			debug_log = "SNW_FILTER|war_start|DUPLICATE_SUPPRESSED"
		}

	}
