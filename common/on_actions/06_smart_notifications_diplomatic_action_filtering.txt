# Phase 4 -- Relational Notification Engine (see TODO.md). Extends the
# Watchlist filtering built for Diplomatic Play events to the generic
# `diplomatic_action_notification` -- the notification any diplomatic
# action (Increase/Decrease Relations, autonomy requests, ...) posts to
# its recipient. Confirmed real complaint from the user (2026-09-07): a
# decentralized rebel faction using Increase Relations popped a toast for
# a country nobody cares about.
#
# Root = Diplomatic Action (`on_diplomatic_action`, confirmed via vanilla's
# own comment in common/on_actions/00_code_on_actions.txt). scope:actor and
# scope:recipient are confirmed real and bound here -- unlike the sibling
# `_third_party_` on_actions (on_diplomatic_action_third_party etc., see
# 04_smart_notifications_probes.txt), which are still genuinely blocked:
# a confirmed real error (`is_player trigger [ Wrong scope for trigger:
# diplomatic_action, expected country ]`) already came from guessing at
# THOSE, but a `04_smart_notifications_probes.txt` probe on this different,
# plain on_action showed `scope:actor`/`scope:recipient` resolving to real
# country names (e.g. "Siam" -> "Champasak") with no error. Same root type,
# different on_action -- the earlier blocked finding does not automatically
# generalize to this one, and didn't.
#
# CONFIRMED WRONG 2026-09-08 via the user's screenshot: our replacement
# keys showed the RAW loc key name on screen
# ("notification_smart_notifications_diplomatic_action_watched_name")
# instead of real text -- the bet that `type = diplomatic_action` alone
# would trigger the same native per-action-type text resolution vanilla's
# own diplomatic_action_notification got was wrong. That resolution is
# tied to the specific vanilla key name, not the `type` field generically.
# Tried `[ROOT.GetName]` as a way to recover the specific action type
# dynamically for our own text -- also confirmed wrong (a real, repeated
# `error.log` "Data error in loc string" entry, same failure class as
# every other wrong dynamic-text guess in this project). No known way to
# tell Increase Relations apart from Decrease Relations etc. from our own
# script/loc. Fixed by giving our replacement keys real, deliberately
# GENERIC name/desc loc (see smart_notifications_l_english.yml) -- loses
# the vanilla per-action-type wording, but renders correctly for every
# action type instead of a broken key for all of them.
#
# SEPARATE bug, same screenshot investigation: the ELEVATED/QUIET
# debug_log lines were ALSO silently failing (their own "Data error in
# loc string" entries) from `SCOPE.sC('actor').GetCountry.GetNameNoFormatting`
# -- chaining `.GetCountry` directly onto a `SCOPE.sC(...)` call is NOT
# the same as `THIS.GetCountry` inside an actual re-scoped
# `scope:actor ?= { ... }` block (which the probe confirmed safe, and the
# per-role diagnostic below still uses). Fixed by dropping `.GetCountry`
# from the two decision-line debug_logs, matching the exhaustively-proven
# `SCOPE.sC('actor').GetNameNoFormatting` pattern (no `.GetCountry`) used
# everywhere else in this mod for the diplomatic_play root -- evidently
# also correct here, once written the same way.
#
# REVISED 2026-09-09 per the user: reported "two notifications about the
# same thing" plus "our own content is useless" for a Junagadh -> Great
# Qing diplomatic action. Root-caused via error.log/debug.log rather than
# guessing: confirmed `smart_notifications_diplomatic_action_watched`
# fired exactly once (no duplicate bug in OUR code), and (WRONGLY)
# concluded the second popup was vanilla's own per-action-type
# notification fired by a separate, hardcoded, unfilterable mechanism --
# so suppressed our own notification whenever `scope:recipient` was the
# player, on the assumption vanilla's own popup would stand alone.
#
# CORRECTED, same day, later (2026-09-09): that "hardcoded/unfilterable"
# claim was wrong. The vanilla per-action-type popup
# (`increase_relations_action_notification_name`/_desc etc.) is resolved
# via `GetDiplomaticAction.GetActionNotificationName`, the SAME dynamic-
# text call behind `notification_diplomatic_action_notification_name` --
# i.e. it IS `diplomatic_action_notification`, a real common/messages/
# key this mod already mutes (notification_type = none, see
# common/messages/00_messages.txt). At the time this suppression was
# added (12:20), that mute was ALSO silently broken by the (then still
# unnoticed) mixed-notification-types bug -- diplomatic_action_notification
# shared a group with 3 `toast` siblings, and per the exact game.log
# timestamp evidence, that mismatch caused the "muted" message to render
# as a toast anyway. That's what was actually showing up as the
# "duplicate" here at the time. Once the mixed-group bug was fixed later
# the same day (see common/messages/00_messages.txt's own comment,
# committed 14:28), vanilla's mute started actually working -- so THIS
# suppression branch and that now-effective mute combined into total
# silence for the exact case that matters most (someone's diplomatic
# action targeting the player directly). Removed the player-recipient
# suppression branch entirely: it's also redundant, not just wrong --
# `smart_notifications_is_watched` already includes `is_player = yes`
# (00_smart_notifications_triggers.txt), so the normal watched-check
# below already elevates this case on its own, with no special-casing
# needed to just GET a toast.
#
# REFINED AGAIN 2026-09-09, same day: user pushed back that the toast's
# own text was "weirdly unspecific" ("X has taken a diplomatic action
# involving Y") even after the title fix above. Re-added a player-
# recipient special case, but as its OWN dedicated message key this
# time (`smart_notifications_diplomatic_action_targeting_player`, see
# common/messages/00_messages.txt) rather than suppression -- the
# player-is-recipient case is the one situation where vanilla's own
# full `_desc` text is actually accurate to reuse (it's written assuming
# the player is a party to the action), so this key's desc uses
# `GetActionNotificationDesc` directly instead of our own generic
# fallback. Must be checked BEFORE the watched-check below since it's a
# strict subset of it. The genuinely-third-party-watched case still
# goes through `smart_notifications_diplomatic_action_watched` with the
# safe generic desc, since vanilla's desc text would misrepresent that
# case (assumes the player is involved when they're not). NOT YET
# LIVE-TESTED.

on_diplomatic_action = {
	on_actions = {
		smart_notifications_diplomatic_action
	}
}

# Root = Diplomatic Action. OR'd across actor and recipient (unlike the
# diplo-play events' any_scope_play_involved, there's no roster to iterate
# here -- just the two countries directly involved) so the notification
# elevates if EITHER side is watched or is the player -- matches the
# established "notifications about the player must never be filtered"
# rule automatically, since is_player = yes is already baked into
# smart_notifications_is_watched (00_smart_notifications_triggers.txt): a
# diplomatic action directed at the player (scope:recipient = us) always
# elevates regardless of watchlist.
smart_notifications_diplomatic_action = {
	effect = {
		if = {
			# ADDED 2026-09-09: the player-as-recipient case gets its OWN
			# message key now, not just elevated priority, so its desc can
			# safely reuse vanilla's full per-action text (see
			# common/messages/00_messages.txt's comment on
			# smart_notifications_diplomatic_action_targeting_player). This
			# must be checked FIRST since it's a strict subset of the
			# `smart_notifications_is_watched` check below (is_player = yes
			# is already part of that trigger) -- without checking this
			# branch first, the watched-country toast would fire instead
			# and this more-specific one never would.
			limit = { scope:recipient ?= { is_player = yes } }

			# REFINED 2026-09-09, same day: user correctly pushed back that
			# "a random country doing a not-very-important action to you"
			# (e.g. a minor improving relations) shouldn't toast the same
			# as something consequential. Initially claimed there's no
			# script-side way to tell action types apart -- wrong, found
			# via docs/triggers.log: `has_diplomatic_pact = { who = X
			# type = Y is_initiator = yes/no }` (confirmed real, already
			# used by vanilla's own increase_relations/damage_relations
			# definitions in common/diplomatic_actions/00_relations_actions.txt)
			# lets us check, from a country scope, whether the actor now
			# holds a specific pact type with the recipient. Increase/
			# Decrease Relations are the routine, high-frequency case this
			# was actually about -- demoted specifically those to their own
			# feed-tier message
			# (smart_notifications_diplomatic_action_targeting_player_routine),
			# same full accurate text, just not a toast. Everything else
			# targeting the player (rivalry, subjugation, embargo,
			# autonomy changes, alliance/pact offers, ...) still toasts.
			# `is_initiator = yes` on the check ties it to THIS actor
			# specifically, not just any pre-existing pact of that type
			# between the two countries from some unrelated earlier event.
			#
			# REFINED AGAIN 2026-09-09, same day: user clarified the
			# routine-demotion should only apply when the ACTOR isn't
			# watched -- a watched country's action against you is worth
			# knowing about even if it's "only" a relations change,
			# precisely because you're tracking that country specifically.
			# The demotion is for the "random unwatched minor doing
			# something routine" case only. (Diplomatic Plays, the user's
			# other example of an "important" type, were never actually
			# affected by this file at all -- those fire through a
			# completely separate, already-elevated on_action from earlier
			# phases, so they're unaffected either way.)
			if = {
				limit = {
					scope:actor ?= {
						NOT = { smart_notifications_is_watched = yes }
						OR = {
							has_diplomatic_pact = { who = scope:recipient type = increase_relations is_initiator = yes }
							has_diplomatic_pact = { who = scope:recipient type = damage_relations is_initiator = yes }
						}
					}
				}
				post_notification = smart_notifications_diplomatic_action_targeting_player_routine
				debug_log = "SNW_FILTER|diplomatic_action|posted_key=smart_notifications_diplomatic_action_targeting_player_routine|actor=[SCOPE.sC('actor').GetNameNoFormatting]|recipient=[SCOPE.sC('recipient').GetNameNoFormatting]|PLAYER_TARGETED_ROUTINE"
			}
			else = {
				post_notification = smart_notifications_diplomatic_action_targeting_player
				debug_log = "SNW_FILTER|diplomatic_action|posted_key=smart_notifications_diplomatic_action_targeting_player|actor=[SCOPE.sC('actor').GetNameNoFormatting]|recipient=[SCOPE.sC('recipient').GetNameNoFormatting]|PLAYER_TARGETED"
			}

			# TEMPORARY diagnostic (2026-09-09) -- the routine-relations
			# demotion above never actually fired in two real sessions
			# (confirmed: Siam -> Great Qing, watched=no, still went to
			# PLAYER_TARGETED not PLAYER_TARGETED_ROUTINE), despite the
			# user reporting exactly a "relations improvement" action.
			# Breaks out each half of the has_diplomatic_pact check
			# individually -- WITH and WITHOUT is_initiator -- to find out
			# whether it's a timing issue (pact not yet registered at this
			# exact on_action pulse) or a wrong is_initiator assumption.
			# Delete once the real cause is found and fixed. Grep debug.log
			# for SNW_PACT_PROBE.
			scope:actor ?= {
				if = {
					limit = { has_diplomatic_pact = { who = scope:recipient type = increase_relations is_initiator = yes } }
					debug_log = "SNW_PACT_PROBE|increase_relations|is_initiator=yes|result=yes"
				}
				else = {
					debug_log = "SNW_PACT_PROBE|increase_relations|is_initiator=yes|result=no"
				}
				if = {
					limit = { has_diplomatic_pact = { who = scope:recipient type = increase_relations } }
					debug_log = "SNW_PACT_PROBE|increase_relations|no_is_initiator|result=yes"
				}
				else = {
					debug_log = "SNW_PACT_PROBE|increase_relations|no_is_initiator|result=no"
				}
				if = {
					limit = { has_diplomatic_pact = { who = scope:recipient type = damage_relations is_initiator = yes } }
					debug_log = "SNW_PACT_PROBE|damage_relations|is_initiator=yes|result=yes"
				}
				else = {
					debug_log = "SNW_PACT_PROBE|damage_relations|is_initiator=yes|result=no"
				}
				if = {
					limit = { has_diplomatic_pact = { who = scope:recipient type = damage_relations } }
					debug_log = "SNW_PACT_PROBE|damage_relations|no_is_initiator|result=yes"
				}
				else = {
					debug_log = "SNW_PACT_PROBE|damage_relations|no_is_initiator|result=no"
				}
			}
		}
		else_if = {
			limit = {
				OR = {
					scope:actor ?= { smart_notifications_is_watched = yes }
					scope:recipient ?= { smart_notifications_is_watched = yes }
				}
			}
			post_notification = smart_notifications_diplomatic_action_watched
			debug_log = "SNW_FILTER|diplomatic_action|posted_key=smart_notifications_diplomatic_action_watched|actor=[SCOPE.sC('actor').GetNameNoFormatting]|recipient=[SCOPE.sC('recipient').GetNameNoFormatting]|ELEVATED"
		}
		else = {
			post_notification = smart_notifications_diplomatic_action_quiet
			debug_log = "SNW_FILTER|diplomatic_action|posted_key=smart_notifications_diplomatic_action_quiet|actor=[SCOPE.sC('actor').GetNameNoFormatting]|recipient=[SCOPE.sC('recipient').GetNameNoFormatting]|QUIET"
		}

		# TEMPORARY instrumentation (2026-09-08), same shape as the
		# diplo-play events' per-participant taps -- explicit watched
		# status for both sides alongside the decision above. `.GetCountry`
		# here matches EXACTLY what 04_smart_notifications_probes.txt
		# already confirmed working for scope:actor/scope:recipient on
		# this specific on_action (real names logged, no error) -- not
		# assumed from the diplomatic_play convention used elsewhere in
		# this mod, which is a different root type. Delete once confirmed
		# tuned correctly. Grep debug.log for SNW_FILTER.
		scope:actor ?= {
			if = {
				limit = { smart_notifications_is_watched = yes }
				debug_log = "SNW_FILTER|diplomatic_action|involved|country=[THIS.GetCountry.GetNameNoFormatting]|role=actor|watched=yes"
			}
			else = {
				debug_log = "SNW_FILTER|diplomatic_action|involved|country=[THIS.GetCountry.GetNameNoFormatting]|role=actor|watched=no"
			}
		}
		scope:recipient ?= {
			if = {
				limit = { smart_notifications_is_watched = yes }
				debug_log = "SNW_FILTER|diplomatic_action|involved|country=[THIS.GetCountry.GetNameNoFormatting]|role=recipient|watched=yes"
			}
			else = {
				debug_log = "SNW_FILTER|diplomatic_action|involved|country=[THIS.GetCountry.GetNameNoFormatting]|role=recipient|watched=no"
			}
		}
	}
}
