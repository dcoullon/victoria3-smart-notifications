# Smart Notifications mod: "notify me when this specific law has more
# support than pushback" opt-in checkbox (see TODO.md's sized backlog,
# item 4, and common/alert_types/01_smart_notifications_alerts.txt's
# smart_notifications_law_commitment_alert). GUI anchor:
# gui/politics_panel_change_law.gui's law detail panel.
#
# REVISED AGAIN 2026-09-08 after the first per-law version (storing the
# flag ON the `law` scope itself) was confirmed NOT working live --
# error.log showed, for every law type tested: "has_variable trigger
# [ This scope doesn't support variables. Scope: Law ... ]". `law` scope
# categorically cannot hold variables in this engine, confirmed directly
# by the engine's own error message, not a guess. The GUI wiring itself
# (`Law.MakeScope`, `.Execute()`/`.IsValid()` dispatch) was ALSO confirmed
# working by that same error log -- it correctly named the exact law
# clicked each time -- so the fix only needed to move WHERE the flag
# lives, not how the checkbox reaches a specific law.
#
# New design: root stays `scope = law` (proven to dispatch correctly),
# but the flag itself lives on the COUNTRY (`THIS.owner`, fully proven
# throughout this whole mod to support variables), using one static,
# per-law-type variable name matched via `THIS.type = law_type:X`
# comparisons -- effects can't build a variable NAME dynamically
# (Concatenate is a GUI/loc-only function, not available here), so this
# needs one branch per real law type. GENERATED 2026-09-08 from every
# law_type key in common/laws/*.txt (138 at generation time, corrected
# from an initial, BOM-related 126 -- see the scripted_trigger file
# above for the fuller writeup) -- see
# common/scripted_triggers/01_smart_notifications_law_wanted_trigger.txt
# for the read-side twin of this mapping (kept in sync, regenerate both
# together). A future DLC/patch adding new law types simply won't have a
# matching branch here until this file is regenerated -- the checkbox
# would silently do nothing for that one new law specifically, not error
# or affect any existing law's entry.
#
# REVISED 2026-09-08, second real bug: the first version of this file
# used `ROOT` to reach the country, which is wrong here -- this SGUI's
# own `scope = law` means ROOT, at the point this effect starts, IS the
# law, not a country (confirmed live: error.log repeated the exact same
# "This scope doesn't support variables. Scope: Law ..." error the first
# fix was meant to resolve, just pointing at a different file). Fixed by
# using `THIS.owner` instead (confirmed real for law scope via
# event_targets.log: "Scope to the owner country of object") -- see the
# scripted_trigger file above for the fuller writeup, since it hit the
# identical mistake the same way.
