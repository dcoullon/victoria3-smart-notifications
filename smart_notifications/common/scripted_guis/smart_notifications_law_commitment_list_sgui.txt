# the specific law name and group, since clicking the alert alone doesn't
# highlight anything -- see that alert's own open_panel comment for why a
# direct link isn't possible).
#
# MOVED here from common/alert_types/01_smart_notifications_alerts.txt
# 2026-09-08, same day, after the law name showed up blank live and
# error.log gave an unambiguous reason: "Promote 'GetScriptedGui' returned
# nullptr" -- the SGUI wasn't found AT ALL when `ExecuteTooltip` looked it
# up, despite parsing fine (validate_syntax.py passed) and despite
# `.Execute()`/`.IsValid()` working fine for every OTHER scripted_gui this
# mod ships. The one structural difference: every other one lives in
# common/scripted_guis/, and this was the only scripted_gui definition
# ever placed in common/alert_types/ instead. Confirmed real: the engine
# only scans common/scripted_guis/ for scripted_gui definitions, not
# arbitrary other common/ subfolders -- moving it here with no other
# change is the fix.
#
# Real, documented vanilla technique (scripted_guis.md "Using SGUIs to
# build lists in loc"): a scripted GUI's `effect` can call
# `custom_tooltip = "LOC_KEY"` once per matching item, and a loc string
# elsewhere can render the whole built list live via
# `[GetScriptedGui('key').ExecuteTooltip(GuiScope.SetRoot(...).End)]` --
# evaluated fresh every time the tooltip renders, not baked into a slow-
# updating variable, so there's no staleness/lag concern the way a
# monthly-pulse-computed value would have.
#
# REVISED AGAIN 2026-09-08, SECOND root cause of the blank law name (the
# folder move above fixed "SGUI not found at all", but the name still
# rendered blank after that): error.log, once the SGUI was actually being
# found and run, showed two further, unambiguous errors every time this
# ran:
#   Could not find data system function 'GetNameNoFormatting' in
#   'THIS.GetNameNoFormatting'.
#   Could not find promote for 'GetGroup' in 'THIS.GetGroup.GetName'.
# i.e. `law` scope has NEITHER a name-getter NOR a `GetGroup` promote in
# the script-side dynamic-text/data-function system (the GUI-binding
# language's `Law.GetGroup`, used by the real vanilla law-list widgets in
# gui/politics_panel_types.gui, is a DIFFERENT function table -- it isn't
# available from `custom_tooltip`/`[...]` context, confirmed by these
# errors, not a guess).
#
# Fixed by dropping dynamic text entirely for this and going fully static
# instead, mirroring the same per-law-type dispatch pattern already used
# by smart_notifications_law_notify_sgui.txt: every law's name AND its
# group both already have their own normal loc keys in vanilla
# (`law_<type>` -> display name, the law's own `group = lawgroup_X` field
# -> `lawgroup_X` display name -- confirmed for all 138 law types by
# checking common/laws/*.txt against localization/english/*.yml), so each
# branch below picks a law-specific loc key
# (`smart_notifications_law_entry_<type>`) whose text is a plain
# `$law_<type>$ ($lawgroup_X$)` inline loc reference -- a confirmed real
# vanilla technique (localization/english/laws_l_english.yml uses
# `"$ideology_carlist$"` the same way) needing no dynamic function call
# at all, so it can't hit this class of error. GENERATED 2026-09-08 from
# the same law_type list as the other two generated files (regenerate
# all three together if the law list ever changes).
